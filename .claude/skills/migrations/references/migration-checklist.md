# Migration Checklist

Run every item on this list before committing a migration to source control.
A failed check is a blocker — fix it before continuing.

---

## 1. Generated code review

### Never accept generated migrations blindly

EF Core generates migrations from model diffs. It is often wrong about:
- Renames (generates DROP + ADD instead of RENAME)
- Index names (generates platform-specific names that differ between devs)
- Default values (omits server-side defaults; adds client-side ones)
- Computed columns (may regenerate as plain columns)

**Check every generated migration line by line before committing.**

### Rename detection

```csharp
// EF Core generates this for a rename — WRONG, loses data
migrationBuilder.DropColumn(name: "FullName", table: "Users");
migrationBuilder.AddColumn<string>(name: "DisplayName", table: "Users");

// Correct replacement
migrationBuilder.RenameColumn(
    name: "FullName",
    table: "Users",
    newName: "DisplayName");
```

If the generated code contains a `DropColumn` immediately followed by an `AddColumn`
of the same type on the same table, it is almost certainly a misdetected rename.
Replace with `RenameColumn`.

## 2. Schema checklist

- [ ] **Migration is named descriptively** — describes the change, not a ticket number.
- [ ] **`Down()` is implemented** and is the exact inverse of `Up()`. Not empty. Not `throw new NotImplementedException()`.
- [ ] **New non-nullable columns** have a `defaultValue` or a backfill step before the constraint is added.
- [ ] **New columns are nullable first** when the column will be populated by a subsequent data migration.
- [ ] **No DROP statements without a preceding code-removal deploy** — the code that reads/writes this column must already be gone.
- [ ] **No renamed columns without a zero-downtime strategy** — see `references/zero-downtime.md`.
- [ ] **Indexes are named explicitly** — do not rely on EF Core's generated index names, which differ across providers.

```csharp
// WRONG — name generated by EF Core, non-deterministic across machines
migrationBuilder.CreateIndex(
    name: "IX_Orders_CustomerId",   // might be different for someone else
    table: "Orders",
    column: "CustomerId");

// CORRECT — name explicitly defined and matches your naming convention
migrationBuilder.CreateIndex(
    name: "ix_orders_customer_id",  // snake_case for PostgreSQL, PascalCase for SQL Server
    table: "Orders",
    column: "CustomerId");
```

- [ ] **Foreign key constraint names are explicit** for the same reason.
- [ ] **`migrationBuilder.Sql()` calls use raw SQL literals** (`"""..."""`) — not string interpolation.
- [ ] **No secrets, environment-specific values, or connection strings** in migration SQL.

---

## 3. Data integrity checklist

- [ ] **Data migrations are in a separate migration file** from schema changes.
- [ ] **Bulk SQL in migrations is batched** — updating millions of rows in a single statement locks the table. Use batched updates (see `references/data-migrations.md`).
- [ ] **Backfill is idempotent** — running `Up()` twice produces the same result (important for `--idempotent` scripts).
- [ ] **Foreign key constraints are added after data is consistent**, not before.
- [ ] **Unique indexes are added after verifying no duplicates exist** (or the migration includes a deduplication step).

---

## 4. Performance checklist

- [ ] **Index creation on large tables uses `CONCURRENTLY`** (PostgreSQL) or `ONLINE = ON` (SQL Server) to avoid table locks.

```csharp
// PostgreSQL — non-blocking index creation
migrationBuilder.Sql(
    """CREATE INDEX CONCURRENTLY IF NOT EXISTS "ix_orders_created_at" ON "Orders" ("CreatedAt");""");

// SQL Server — non-blocking index creation
migrationBuilder.Sql(
    """CREATE INDEX ix_Orders_CreatedAt ON Orders (CreatedAt) WITH (ONLINE = ON);""");
```

- [ ] **`NOT NULL` constraints on large tables** are added in two steps (add nullable → backfill → make non-nullable) to avoid full table scans with a lock.
- [ ] **`AlterColumn` on a large table** — check whether the underlying engine requires a table rewrite (PostgreSQL usually does not; SQL Server often does for type changes).
- [ ] **Migration estimated duration** — for tables over 1 million rows, estimate the time the migration will take in staging before scheduling a production window.

## 5. Preview SQL

Always generate and read the SQL script before applying to any shared environment:

```bash
# Idempotent script (safe to run multiple times — checks __EFMigrationsHistory)
dotnet ef migrations script --idempotent \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api \
  --output migrations-preview.sql

# Script for a specific range
dotnet ef migrations script PreviousMigrationName CurrentMigrationName \
  --project Src/MyApp.Infrastructure \
  --output migrations-preview.sql
```

Read `migrations-preview.sql` and verify:
- No unexpected `DROP` statements
- No `ALTER COLUMN` on the wrong table
- `IF NOT EXISTS` / idempotency guards are present where expected
- The statement count matches the number of structural changes you intended

---

## 6. Snapshot consistency

- [ ] **`ModelSnapshot.cs` is committed in the same commit as the migration** — never separately.
- [ ] **No manual edits to `ModelSnapshot.cs`** — it is always regenerated by EF Core.
- [ ] **After a merge conflict in `ModelSnapshot.cs`**, regenerate it:

```bash
# After resolving model conflicts, remove the snapshot and regenerate
dotnet ef migrations remove --project Src/MyApp.Infrastructure
dotnet ef migrations add <MigrationName> --project Src/MyApp.Infrastructure
```

---

## 7. Environment parity

- [ ] **Migration tested on a copy of the production database schema** (not just dev/empty DB).
- [ ] **Rollback tested** — apply migration, then run `dotnet ef database update <PreviousMigration>`, verify schema is identical to before.
- [ ] **Idempotent script verified** — run the script twice; no errors on the second run.

---

## Quick reference: common EF Core CLI commands

```bash
# Add a migration
dotnet ef migrations add <Name> \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# Apply all pending migrations
dotnet ef database update \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# Roll back to a specific migration
dotnet ef database update <MigrationName> \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# Roll back ALL migrations (empty database)
dotnet ef database update 0 \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# Remove the last unapplied migration
dotnet ef migrations remove \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# List migrations and their applied status
dotnet ef migrations list \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api

# Generate idempotent SQL script for all pending
dotnet ef migrations script --idempotent \
  --project Src/MyApp.Infrastructure \
  --startup-project Src/MyApp.Api \
  --output pending.sql

# Generate script for a specific range
dotnet ef migrations script <From> <To> \
  --project Src/MyApp.Infrastructure \
  --output range.sql
```
